# CROUS 技术路线

## 实现方式

本版通过 AI Coding 完成产品结构、交互、业务模型、云端接口、数据校验与部署。推荐采用可解释规则，便于演示偏好如何影响结果。

| 层 | 选型 | 职责 |
| --- | --- | --- |
| 交互界面 | HTML、CSS、原生 JavaScript | 学生／商家双端、弹窗、转盘、订单、点评、响应式布局 |
| 业务模型 | CampusModel | 窗口、菜品、偏好、订单状态、评分更新与本机保存 |
| 页面与 API | Vinext / React 页面入口 | 登录入口、承载应用、提供 `/api/state` |
| 登录与访问 | Sites / ChatGPT 身份 | 获取稳定账号ID，按当前账号保存数据 |
| 数据 | Cloudflare D1 + Drizzle | 持久化账号体验快照、版本号与更新时间 |
| 部署 | Cloudflare Workers / Sites | 发布页面、静态资产与 API，保持当前访问范围 |
| 仓库 | GitHub | 源代码、迁移、测试、项目说明与技术说明 |

## 数据模型

浏览器业务状态包含 `shops / dishes / prefs / favorites / reviews / orders / wishes`。

| 对象 | 关键字段 |
| --- | --- |
| 窗口 | 名称、食堂楼层窗口、营业时间、排队人数、等待分钟、送寝开关、公告 |
| 菜品 | 窗口ID、名称、价格、口味标签、食材、饮食目标、在售与新品标记、评分 |
| 点评 | 菜品ID、评分、文字、标签、可选实拍、商家回复 |
| 预约 | 菜品、窗口、数量、单价、自取／送寝、时段、地址、备注、总价、状态 |
| 偏好 | 近期饮食目标、口味、预算、忌口 |
| 想吃建议 | 内容、支持人数、当前账号支持状态、食堂回应 |

云端 `crous_user_states` 保存 `user_id / state / revision / updated_at`。采用账号快照是为了让个人体验沙盒完整、部署简单、切端联动清晰。它适合当前 MVP；真实校园多人共用市场需改成窗口、菜品、点评与订单的独立表，并建立真实商家权限。

## 推荐规则

`eligible()` 首先过滤已下架菜品、休息窗口、预算外菜品及含忌口食材的菜品。

排序分数：`评分 × 10 + 目标匹配 × 18 + 口味匹配数 × 6 − min(等待分钟, 20) × 0.4`。

今日首选取排序首位。转盘在最多8道合适菜品或对应窗口中等概率抽取，SVG 扇区旋转与结果一致。所有规则都可在 `public/app/core.js` 中调整。

## 保存与同步

1. `boot.js` 从 `/api/state` 读取当前账号快照与版本。
2. 浏览器按账号隔离本机缓存；修改先保存本机，再延迟600ms同步。
3. API 验证身份、同源来源、请求体大小、对象关系、枚举、数值与图片格式。
4. 写入以旧版本为条件，成功后版本加一；冲突返回409。
5. 同步失败保留本机未同步标记。再次打开时不直接覆盖未同步更改，用户可重试、导出或确认读取云端版本。

云端接口不能让调用者传入另一个用户ID；账号来自平台注入的身份。每个账号拥有独立体验空间，两端角色切换是在这一空间内演示。

## 图片与边界

菜品默认使用项目自绘 SVG 插画。点评上传在浏览器把图片缩放至最长边640px并转JPEG，限制存入快照的图片大小；不会自动调用第三方图片服务。

预约、支付、送寝和排队属于演示业务，没有真实资金处理或外部配送调用。当前没有大模型推理或营养测量服务；饮食目标标签来自商家示例填写。

## 代码目录

```text
app/                 登录页面入口与 /api/state
public/app/          产品界面、主题、转盘与业务模型
lib/state-validation.ts  云端数据校验
db/                  Drizzle 数据表声明
drizzle/             可审查的SQL迁移与版本元数据
tests/               核心业务、界面生成与同步测试
docs/                产品说明、技术路线、验证记录
build/、scripts/     Sites 运行与构建支持
```

## 运行与部署

Node.js 22.13+，建议使用仓库中的 pnpm 锁文件。`pnpm install`、`pnpm dev`、`pnpm test`、`pnpm typecheck`、`pnpm build`。

云端 D1 绑定由 `.openai/hosting.json` 中的 `d1: DB` 声明，迁移通过 `pnpm db:generate` 生成。部署由 Sites 应用迁移并发布 Worker。克隆到新的部署项目时，需使用自己的 Site 身份和绑定，不应直接复用原项目ID。
