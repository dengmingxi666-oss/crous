# CROUS 项目说明

## 产品定位

CROUS「食物法庭」是大学生的校园食堂点评推荐工具。它把选择下一顿、表达真实口味与窗口回应组织成一套可持续体验的流程。

核心场景：学生下课后预算有限、不知道吃什么；看过别人的“好吃”推荐，却不确定口味、分量或排队情况是否适合自己。

## 目标与用户

| 用户 | 要完成的事 | 产品响应 |
| --- | --- | --- |
| 学生 | 快速决定吃什么 | 今日首选、按口味推荐、转盘 |
| 学生 | 发现新菜、降低踩雷概率 | 新菜上庭、实拍证词、多维反馈、评价人数 |
| 学生 | 少走路、少等候 | 窗口具体位置、营业状态、排队人数与等待时间 |
| 学生 | 按自己需求吃 | 预算、忌口、口味、均衡／减脂／增肌偏好 |
| 学生 | 安排取餐与反馈 | 预约时段、自取／模拟送寝、订单进度、评价 |
| 窗口商家 | 让学生看到最新菜单 | 菜品发布、维护、上架、下架与新品标记 |
| 窗口商家 | 有序处理需求 | 预约接单、状态推进、排队维护、点评回应 |

## 信息结构

学生端：今日开庭 → 食堂窗口 → 今天吃什么 → 夯味榜 → 我的订单 → 口味档案。

商家端：经营概览 → 菜品管理 → 订单预约 → 点评答辩 → 店铺设置 → 产品结构。

菜品是点评与推荐的基本单位。每道菜归属一个窗口，窗口显示所属食堂、楼层、位置、营业时间、公告与预计等待时间。

## 关键流程

### 发现与决策

1. 学生设置近期目标、口味、预算与不想吃的食材。
2. 推荐列表先过滤预算外、含忌口食材、已下架与休息窗口的菜品，再排列合适的选项。
3. 今日首选取推荐列表首位；详情显示推荐依据。
4. 转盘在筛选后的候选中随机选择，学生仍可查看点评后再决定。

### 点评与商家回应

学生评分 → 选择具体标签 → 填写口味、分量、价格或等待体验 → 可选上传实拍 → 发布证词 → 商家回复。

用「夯爆了」「申请复吃」「分量正义」「排队劝退」增加校园语感。星级、文字与评价人数仍展示出来；趣味判词由评分区间生成，仅作为口碑表达。

### 预约与模拟履约

选择菜品 → 自取或送寝 → 选择份数、时段 → 填写寝室与备注 → 确认预约 → 商家接单 → 制作 → 待取餐／配送中 → 完成。

学生只能取消尚未接单的预约。送寝只对商家开启此能力的窗口开放，费用示例为每单2元；不会产生真实扣款。

### 上新与持续供给

商家发布菜品后，学生端菜单与新品区直接展示。学生可提交“想吃什么”和支持票，商家在经营概览中回复试做、上新或替代方案。

## 状态与反馈

- 菜品无评价：显示“待评分／等待开庭”。
- 筛选无结果：提示调整预算、忌口或分类。
- 窗口休息、菜品下架：退出推荐与转盘，无法预约。
- 云端保存中、成功、失败或冲突：明确展示状态并提供重试、导出和读取云端版本。
- 云端失败：保留本机更改，下次打开识别未同步记录，避免直接覆盖。
- 恢复演示：需要确认，清除当前账号体验记录并还原示例数据。

## 验收建议

| 检验 | 预期行为 |
| --- | --- |
| 修改预算与忌口 | 今日首选和转盘候选随之变化 |
| 商家下架菜品 | 学生端不再推荐或接受新预约 |
| 商家发布新菜 | 菜单与新菜区域出现新品 |
| 学生预约送寝 | 订单包含地址、时段、备注和示例费用 |
| 商家推进订单 | 学生看到相同订单的新状态 |
| 学生点评、商家回复 | 同一菜品详情显示评价与回应 |
| 刷新或同账号换设备 | 读取已保存的账号体验记录 |

## 后续真实校园试点

优先补充真实窗口与菜单数据，再验证学生是否更快完成就餐选择、点评是否有帮助、商家是否愿意持续维护。真实试点需加入商家审核与权限、共享校园内容库、排队数据来源、支付及配送履约；本版已用明确的体验状态展示这些产品路径。
